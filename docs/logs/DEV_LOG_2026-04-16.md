# Optimus Biped — Dev Log 2026-04-16

## Goal
Get the CPG walking algorithm running on real hardware: ESP32-C3 Super Mini → PCA9685 → 8× MG995 servos, wired to match the legacy biped robot channel layout.

---

## Bug 1 — FQBN: `USBMode` option does not exist

**Symptom:** `arduino-cli compile` failed immediately:
```
Error: Invalid FQBN: invalid option 'USBMode'
```
**Root cause:** The `sketch.yaml` was copied from another project targeting a different ESP32 variant. The installed `esp32:esp32` core version (3.3.8) does not expose a `USBMode` option for the C3 — `CDCOnBoot=cdc` alone is sufficient.

**Fix:** Removed `USBMode=hwcdc` from both `Makefile` and `sketch.yaml`:
```
# Before
esp32:esp32:esp32c3:USBMode=hwcdc,CDCOnBoot=cdc,PartitionScheme=huge_app
# After
esp32:esp32:esp32c3:CDCOnBoot=cdc,PartitionScheme=huge_app
```

## Bug 2 — Compile error: `volatile` struct assignment

**Symptom:**
```
error: passing 'volatile IMUEstimate' as 'this' argument discards qualifiers
error: passing 'volatile LegAngles' as 'this' argument discards qualifiers
```
**Root cause:** Shared globals `g_imu_estimate` and `g_leg_angles` were declared `volatile`. The compiler-generated `operator=` is not `volatile`-qualified so the assignment is rejected.

**Fix:** Replaced both struct assignments with `memcpy` through a void pointer:
```cpp
memcpy((void*)&g_imu_estimate, &est,    sizeof(IMUEstimate));
memcpy((void*)&g_leg_angles,   &angles, sizeof(LegAngles));
```

## Bug 3 — Runtime crash: `xTaskCreatePinnedToCore` assert

**Symptom:** Board booted, reached task creation, then panicked:
```
assert failed: xTaskCreatePinnedToCore ... (xCoreID < 1)
```
**Root cause:** All three FreeRTOS tasks were pinned to core `1`. The ESP32-C3 is **single-core** — only core `0` exists.

**Fix:** Changed all `xTaskCreatePinnedToCore` calls to core `0`:
```cpp
xTaskCreatePinnedToCore(task_cpg, "cpg", ..., nullptr, 0);
```

## Bug 5 — GPIO 22 does not exist on ESP32-C3

**Symptom:** I2C scan found no devices. `PCA9685 OK` printed anyway (separate bug, see #6).

**Root cause:** `config.h` had `I2C_SCL_PIN = 22`. The ESP32-C3 Super Mini only exposes GPIOs 0–10, 20, 21. GPIO 22 does not exist — the SCL line was floating.

**Fix:**
```c
#define I2C_SDA_PIN  8
#define I2C_SCL_PIN  9
```

## Bug 6 — PCA9685 falsely reports "OK" when not present

**Symptom:** Even with GPIO 22 (invalid), serial printed `[SERVO] PCA9685 OK`. The presence check was:
```cpp
uint8_t mode1 = read_reg(PCA9685Reg::MODE1);
if (mode1 == 0xFF) return false;
```
**Root cause:** When no device is on the bus, `Wire.requestFrom()` returns 0 bytes and `read_reg` returns `0`. Since `0 ≠ 0xFF`, the check passed.

**Fix:** Replaced with an explicit ACK check:
```cpp
Wire.beginTransmission(addr_);
if (Wire.endTransmission() != 0) return false;
```

## Bug 7 — PCA9685 register writes silently failing (all readbacks = 0)

**Symptom:** Added register readback to `set_angle()`. Every write showed `MISMATCH!`:
```
[PCA9685] ch0  20.0° → 1661us tick=340  readback=0 MISMATCH!
```
Servos were connected, powered, and PCA9685 was ACKing on I2C — but physically not moving.

**Root cause:** The **Auto-Increment (AI) bit** (MODE1 bit 5) was never set. Without it, a multi-byte I2C burst write (used by `set_pwm` to write 4 bytes: ON_L, ON_H, OFF_L, OFF_H) does not advance the internal register pointer — all 4 bytes land on the same register. The OFF register stays at 0, producing no pulse width.

**Fix:** Rewrote the `begin()` init sequence to explicitly set AI=1:
```cpp
write_reg(PCA9685Reg::MODE1, 0x10);  // SLEEP=1 (required before prescaler write)
delay(5);
write_reg(PCA9685Reg::PRESCALE, prescale);
write_reg(PCA9685Reg::MODE1, 0x20);  // AI=1, SLEEP=0
delay(5);
write_reg(PCA9685Reg::MODE1, 0xA0);  // RESTART=1, AI=1
delay(5);
```
After this fix readbacks matched and servos moved immediately.

## Bug 8 — Wrong pulse range → halt positions off

**Symptom:** Servos moved but resting positions were visibly wrong compared to the robot's known good halt pose.

**Root cause:** Firmware used MG995 datasheet range (500–2400 µs). The old robot (`servos_lib.py`) used 600–2650 µs. Center (0°) maps to different pulse widths:
- 500–2400 µs → center = 1450 µs
- 600–2650 µs → center = 1625 µs

The 175 µs difference shifted every servo's halt position.

**Fix:** Matched firmware to old robot:
```c
#define SERVO_PWM_MIN  600   // µs
#define SERVO_PWM_MAX  2650  // µs
```
The per-servo `SERVO_OFFSET_DEG_*` values (derived as `halt_deg − 90`) are now correct.

## Bug 9 — Feet sliding, no lift, walking sideways

**Symptom:** Robot moved but feet dragged along the floor. No lift. Body rotated CCW viewed from top.

**Root cause (phase):** `CPG_PHASE_KNEE_OFFSET = -π/4` caused the knee to start bending *after* the foot had already planted — producing drag not lift. Also `CPG_HIP_PITCH_BASE_PHASE = π` was added to fix backward direction but not propagated to the knee formula, putting knee π out of phase with hip.

**Root cause (direction):** `SERVO_DIR_R_KNEE` was incorrectly changed to `-1`. With anti-phase CPG, the right knee CPG signal is already negated relative to the left. Applying dir=-1 on top negated it again → both knees bent simultaneously → no alternating lift → CCW body rotation.

**Fix:**
- `SERVO_DIR_R_KNEE = +1` (restore original — anti-phase is handled by the CPG, not the direction table)
- `CPG_PHASE_KNEE_OFFSET = 0` (knee in-phase with hip pitch: foot is up during forward swing)
- `CPG_HIP_PITCH_BASE_PHASE = 0` (forward direction confirmed with correct knee phase)
- Apply `CPG_HIP_PITCH_BASE_PHASE` to knee formula in `cpg.cpp` so all joints stay consistent

---

## Bug 10 — Walking backward

**Symptom:** After phase fixes, robot walked but in reverse.

**Root cause:** Multiple sign flips during debugging left the net hip pitch direction inverted. The hip pitch CPG value was positive-forward in the math but negative-forward physically.

**Fix:** Traced the full physical chain:
- `SERVO_DIR_L_HIP_PITCH = +1` (set_inverse=False, ch13) — positive CPG = servo increases = forward swing ✓
- `SERVO_DIR_R_HIP_PITCH = -1` (set_inverse=True, ch2) — positive CPG × (−1) = servo decreases = forward swing ✓ (right side is mechanically mirrored)
- `CPG_HIP_PITCH_BASE_PHASE = 0` confirmed correct with these directions
